# IPTV

سازندهٔ خودکار پلی‌لیست IPTV با پایتون: جمع‌آوری منابع عمومی، افزودن کانال‌های دستی، انتخاب بهترین **لینک سالم**، دسته‌بندی و انتشار فایل‌های M3U. این پروژه سرور ویدئو یا پلیر نیست و محتوای کانال‌ها را میزبانی نمی‌کند.

## استفاده از پلی‌لیست‌ها

لینک زیر را در پلیر سازگار با M3U، مانند VLC یا Kodi، باز کنید:

```text
https://raw.githubusercontent.com/4kings6114/IPTV/main/playlist.m3u
```

خروجی‌های موضوعی در همان مسیر قرار دارند:

| فایل | محتوا |
| --- | --- |
| `playlist.m3u` | همهٔ کانال‌ها |
| `persian.m3u` | تلویزیون، اخبار، فیلم و موزیک فارسی |
| `news.m3u` | اخبار فارسی، انگلیسی و سایر زبان‌ها |
| `music.m3u` | موسیقی |
| `sports.m3u` | ورزش |
| `movies.m3u` | فیلم و سریال |
| `kids.m3u` | کودک و کارتون |
| `favorites.m3u` | کانال‌های انتخاب‌شده در `favorites.json` |
| `profile-fa-en.m3u` | کانال‌های دارای زبان فارسی/انگلیسی قابل‌شناسایی |
| `profile-low-bandwidth.m3u` | نسخه‌های با ارتفاع شناخته‌شدهٔ حداکثر 720p |
| `index.html` | داشبورد مستقل و قابل‌جست‌وجوی آخرین انتشار |
| `playlist-backup.m3u` | نسخهٔ قبلی پلی‌لیست اصلی، هنگام تغییر محتوای آن |

فایل‌های موضوعی ممکن است هم‌پوشانی داشته باشند. آدرس‌های EPG در یک ویژگی `url-tvg` با جداکنندهٔ کاما نوشته می‌شوند؛ پشتیبانی دقیق از چند EPG به پلیر بستگی دارد.

## اجرا

**Python 3.10 یا جدیدتر روی Linux/macOS** کافی است؛ برنامه و تست‌ها به پکیج خارجی نیاز ندارند. قفل هم‌زمانی محلی از `fcntl` استفاده می‌کند.

```bash
# ساخت و انتشار در پوشهٔ پروژه؛ نیازمند اینترنت به منابع و میزبان استریم‌ها
python build_playlist.py

# جمع‌آوری، بررسی و اعتبارسنجی بدون تغییر خروجی‌های منتشرشده
python build_playlist.py --dry-run

# نادیده‌گرفتن کش سلامت و انجام بررسی تازه
python build_playlist.py --dry-run --force-check

# بررسی اختیاری کوتاه با ffmpeg/ffprobe؛ نصب ابزارها جداگانه است
python build_playlist.py --output-dir /tmp/iptv-preview --playback-checks

# ساخت در پوشه‌ای جدا، با همان ورودی‌ها و تنظیمات
python build_playlist.py --output-dir /tmp/iptv-preview

# استفاده از فایل تنظیمات دیگر
python build_playlist.py --config /path/to/config.json --output-dir /tmp/iptv-preview
```

مسیر فایل‌های ورودی (از جمله `manual_file`، `exclude_file`، `overrides_file`، علاقه‌مندی‌ها، پروفایل‌ها و aliasهای EPG) نسبت به **پوشهٔ فایل تنظیمات** محاسبه می‌شود. مسیر نسبی کش نسبت به **پوشهٔ خروجی** است. حالت `--dry-run` می‌تواند کش منابع و گزارش اجرای موقت را به‌روز کند، اما فایل‌های منتشرشده، بکاپ، تاریخچهٔ سلامت لینک‌ها و تاریخچهٔ نمونه‌گیری پخش را تغییر نمی‌دهد.

## محافظت از خروجی

پیش‌فرض‌های مهم در `config.json`:

| تنظیم | پیش‌فرض | کاربرد |
| --- | --- | --- |
| `max_drop_ratio` | `0.3` | افت بیش از ۳۰٪ نسبت به تعداد قبلی، انتشار را متوقف می‌کند |
| `min_channels` | `1` | خروجی خالی هرگز منتشر نمی‌شود |
| `min_available_source_ratio` | `0.8` | حداقل ۸۰٪ منابع باید تازه یا دارای کش معتبر باشند |
| `source_cache_max_age_hours` | `168` | کش هر منبع تا ۷ روز برای بازیابی قابل استفاده است |
| `failure_threshold` | `2` | لینک قبلاً منتشرشده پس از اولین اجرای ناموفق، موقتاً حفظ می‌شود |
| `backup_keep` | `7` | حداکثر ۷ نسخهٔ یکتای قبلی در کش نگه‌داری می‌شود |
| `max_workers` | `20` | تعداد بررسی‌های هم‌زمان لینک |
| `timeout` | `7` | مهلت عملیات شبکه برای هر درخواست استریم، برحسب ثانیه |
| `link_attempts` | `2` | تعداد تلاش برای خطاهای موقت مانند قطع ارتباط و HTTP 5xx |
| `check_segments` | `false` | بررسی اختیاری یک قطعهٔ HLS، علاوه بر خود پلی‌لیست |

اگر بررسی ایمنی رد شود، برنامه با کد غیرصفر خارج می‌شود و خروجی‌های موجود و تاریخچهٔ سلامت را دست‌نخورده نگه می‌دارد. علت در `.cache/iptv/last_run.json` ثبت می‌شود. ابتدا علت را بررسی کنید؛ برای کاهش عمدی تعداد کانال‌ها، فقط محدودیت درصد افت را می‌توان صریحاً کنار گذاشت:

```bash
python build_playlist.py --dry-run --allow-large-drop
# فقط پس از بررسی نتیجه:
python build_playlist.py --allow-large-drop
```

این گزینه محدودیت حداقل کانال یا دسترس‌پذیری منابع را غیرفعال نمی‌کند.

همهٔ خروجی‌ها ابتدا تولید و اعتبارسنجی می‌شوند، سپس با جایگزینی اتمی هر فایل منتشر می‌شوند. در خطاهای معمول نوشتن، فایل‌های جایگزین‌شده بازگردانی می‌شوند. این سازوکار تراکنش چندفایلی در برابر قطع برق نیست؛ هنگام انتشار ممکن است خواننده برای لحظه‌ای نسل‌های متفاوت فایل‌ها را ببیند. پلی‌لیست اصلی آخر از همه جایگزین می‌شود.

## منابع و تنظیمات

`config.json` شامل کشورهای مجاز/مسدود، کلمات مسدود، منابع، EPG و تنظیمات بررسی است. کلید ناشناخته یا نوع مقدار نادرست باعث توقف می‌شود تا اشتباه تایپی نادیده نماند.

- `stream_template` برای هر کشور مجاز یک منبع می‌سازد؛ با مقدار `""` می‌توان دریافت منابع کشوری را غیرفعال کرد.
- `extra_sources` می‌تواند آدرس ساده یا شیء دارای `url`، `country`، `language` و `allow_unknown_country` باشد.
- کشور واقعی `tvg-id` بر کشور پیش‌فرض منبع اولویت دارد؛ `gb` و `uk` یکسان‌سازی می‌شوند.
- فقط منابعی که صریحاً `allow_unknown_country: true` دارند، کانال فاقد کشور مشخص را قبول می‌کنند. کانال‌های دستی نیز می‌توانند فاقد کد کشور باشند.
- برای اجرای صرفاً دستی، `stream_template` را خالی و `extra_sources` را `[]` کنید. محافظ‌های تعداد کانال همچنان فعال‌اند.

دریافت هر منبع باید M3U قابل تجزیه با حداقل یک کانال باشد؛ پاسخ HTML یا خالی کش سالم را جایگزین نمی‌کند. در خطای دریافت، کش همان منبع با تاریخ انقضا استفاده می‌شود. کش و تاریخچه در `.cache/iptv` هستند و وارد Git نمی‌شوند.

## افزودن و حذف دستی

کانال را با قالب زیر به `manual.m3u` اضافه کنید:

```m3u
#EXTM3U
#EXTINF:-1 tvg-id="Example.us" tvg-language="en" group-title="اخبار - انگلیسی",Example News
https://example.com/live/playlist.m3u8
```

برای حذف، در `exclude.txt` هر خط یکی از موارد زیر باشد:

```text
# نام به‌صورت بخشی از نام کانال و بدون حساسیت به بزرگی حروف
Unwanted Channel
# یا آدرس کامل و دقیق
https://example.com/unwanted/playlist.m3u8
```

فایل‌های دستی و حذف‌ها ورودی هستند و برنامه یا مرحلهٔ انتشار آن‌ها را بازنویسی نمی‌کند. لینک‌های قدیمیِ حذف‌شده یا مسدودشده از طریق بازیابی نیز برنمی‌گردند.

## اصلاح نام، گروه و زبان

در `overrides.json` می‌توان اصلاحات را با شناسهٔ کانال یا نام آن نوشت:

```json
{
  "channels": {
    "SuperExpressTV.pl": {"group": "اخبار - سایر زبان‌ها", "language": "pl"},
    "CinemaxHits.us": {"group": "فیلم - انگلیسی‌زبان", "language": "en"},
    "Unwanted.us": {"disabled": true}
  },
  "names": {
    "Example Channel": {"name": "نام نمایشی جدید", "group": "گروه دلخواه"}
  }
}
```

فیلدهای مجاز: `name`، `group`، `language`، `country`، `logo` (آدرس HTTP/S)، `category` و `disabled`. شناسهٔ بدون پسوند `@` بر همهٔ نسخه‌های همان کانال اعمال می‌شود؛ اصلاح یک نسخهٔ مشخص، اولویت بالاتری دارد. نام‌ها بدون کیفیت و بدون حساسیت به بزرگی حروف تطبیق داده می‌شوند.

ترتیب تصمیم‌گیری: اصلاحات صریح → گروه دستی → اطلاعات صریح منبع / مرجع شناسه‌دار → راهنمای زبان منبع → قواعد نام. کشور به‌تنهایی زبان فارسی را اثبات نمی‌کند. تشخیص خودکار کامل نیست؛ موارد مبهم را با اصلاحات صریح تعیین کنید.

## بررسی سلامت و لینک‌های جایگزین

- نسخه‌های کیفیتی یک `tvg-id` تا پایان بررسی حفظ می‌شوند؛ ابتدا لینک‌های سالم و سپس ترجیح صریح منبع (اگر تنظیم شده باشد) و بالاترین کیفیت انتخاب می‌شود. کیفیت از نام یا اندازهٔ اعلام‌شده در HLS master به دست می‌آید، نه اندازه‌گیری بیت‌ریت واقعی.
- پسوندهای کیفیت مانند `@SD` و `@HD` یکسان‌سازی می‌شوند؛ فیدهای منطقه‌ای مانند `@East` و `@West` جدا می‌مانند.
- درخواست محدود `GET` استفاده می‌شود؛ HTML/JSON یا پاسخ خالی حتی با HTTP 200 سالم محسوب نمی‌شود.
- HLS master به پلی‌لیست فرزند دنبال می‌شود؛ با فعال‌کردن `check_segments`، یک قطعه هم بررسی می‌شود.
- هدرهای VLC/Kodi و گزینه‌های هدر در URL هنگام تست استفاده می‌شوند.
- وضعیت‌های `healthy`، `restricted`، `timeout`، `http_error`، `network_error`، `invalid` و `unchecked` از هم جدا هستند. پاسخ 401/403 اثبات پخش‌پذیری یا تشخیص قطعی محدودیت جغرافیایی نیست.
- لینک سالم جایگزین همیشه بر لینک قدیمیِ ناموفق اولویت دارد. مهلت `failure_threshold` فقط برای درخواست قبلاً منتشرشده است، نه ورود لینک خراب جدید. تلاش‌های مجدد یک اجرا، یک مشاهدهٔ ناموفق حساب می‌شوند.
- تاریخچه پس از ساخت پذیرفته‌شده ذخیره می‌شود؛ حذف کش، شمارندهٔ خطاهای متوالی را بازنشانی می‌کند. لینک موقتاً حفظ‌شده در گزارش «تأییدنشده» است، نه سالم.
- `check_links: false` بررسی را صریحاً غیرفعال می‌کند؛ خروجی حاصل تأیید سلامت ندارد و شمارندهٔ خطا/آخرین موفقیت را تغییر نمی‌دهد.
- `drop_dead: false` اجازه می‌دهد کانال فاقد لینک سالم هم به‌صورت تأییدنشده نگه داشته شود؛ این گزینه برای عیب‌یابی است و برای انتشار عادی توصیه نمی‌شود.

بررسی شبکه، تضمین پخش در همهٔ کشورها و پلیرها نیست. DASH فقط از نظر ساختار manifest بررسی می‌شود؛ در بررسی عادی رمزگشایی DRM یا دیکود ویدئو انجام نمی‌شود. نمونه‌برداری HLS نیز فقط یک قطعه را بررسی می‌کند.

## اطلاعات مرجع کانال‌ها

تنظیم `metadata.urls` به API رسمی [iptv-org](https://github.com/iptv-org/api) اشاره می‌کند: `channels.json`، `feeds.json` و `logos.json` در `https://iptv-org.github.io/api/`. زبان در طرح فعلی عمدتاً در feedهاست، نه رکورد کانال؛ فیدهای منطقه‌ای و زبان‌های مبهم به‌جای حدس‌زدن خالی می‌مانند.

- تطبیق خودکار **فقط بر اساس شناسه** است. نام رسمی، کشور، موضوع، زبانِ قابل‌تعیین و لوگوی گمشده تکمیل می‌شوند؛ نام/گروه دستی و اصلاحات صریح اولویت دارند. نشانهٔ کیفیت نام حفظ می‌شود.
- نام‌های مشابه بدون شناسه به هم ادغام نمی‌شوند؛ موارد دارای چند نامزد در `metadata.ambiguous_examples` گزارش می‌شوند. اصلاح را با `overrides.json` انجام دهید.
- `refresh_hours: 24` فاصلهٔ دریافت مرجع، `cache_hours: 168` حداکثر عمر بازیابی و `max_bytes: 33554432` سقف هر پاسخ و دادهٔ بازشدهٔ gzip است. دادهٔ خراب/خالی کش معتبر را جایگزین نمی‌کند. شکست مرجع، ساخت استریم‌ها را متوقف نمی‌کند.
- برای اجرای کاملاً آفلاین `metadata.urls` را `[]` کنید. `metadata.file` اختیاری است و آرایهٔ JSON با همان طرح کانال/feed/logo می‌پذیرد؛ خطای فایل محلی صریح، خطای تنظیمات است و پنهان نمی‌شود.

## اعتبارسنجی واقعی EPG

`epg.enabled: true` دریافت محدود XMLTV یا gzip، ساختار XML، شناسه‌های تعریف‌شده و بازهٔ زمانی برنامه‌ها را بررسی می‌کند. DTD/entity و فایل بیش‌ازحد بزرگ پذیرفته نمی‌شوند. کش آخرین راهنمای سالم تا `epg.cache_hours` (۲۴ ساعت) قابل‌بازیابی است، اما برنامه‌های منقضی حتی از کش، «دارای پوشش» اعلام نمی‌شوند.

- پوشش یعنی شناسهٔ کانال برنامه‌ای با پایان در آینده و شروع حداکثر تا `freshness_hours` ساعت آینده دارد؛ تضمینِ پخش برنامهٔ فعلی یا نبود شکاف در جدول نیست. برنامه‌های بدون تاریخ معتبر، شناسه‌های بدون برنامه و برنامه‌های منقضی جدا گزارش می‌شوند.
- تطبیق با ID واقعی XMLTV انجام می‌شود؛ **شباهت نام، تطبیق EPG نیست**. ارائه‌دهندگانی مانند epg.pw ممکن است ID متفاوت/عددی داشته باشند. برای نگاشت مطمئن، `epg_aliases.json` را با ID واقعاً موجود در راهنما تکمیل کنید:

```json
{
  "channels": {
    "Example.us": "actual-id-from-your-xmltv"
  }
}
```

این نمونه صرفاً قالب است؛ نگاشت نادرست را به فایل واقعی اضافه نکنید. وقتی هدف در راهنمای معتبر وجود دارد، `tvg-id` برای پلیر اصلاح و شناسهٔ اصلی در `x-original-tvg-id` حفظ می‌شود؛ هویت کانال، اصلاحات و علاقه‌مندی‌ها تغییر نمی‌کنند. پسوندهای منطقه‌ای بی‌اجازه به یکدیگر نگاشت نمی‌شوند.

`epg.keep_unverified: true` پیش‌فرض محافظه‌کارانه است: حتی در خرابی راهنما، URLهای پیکربندی‌شده در هدر حفظ و مشکل در گزارش مشخص می‌شود؛ خود استریم حذف نمی‌شود. با `false` فقط راهنماهای دریافت‌شده/کش‌شدهٔ دارای برنامهٔ غیرمنقضی در هدر قرار می‌گیرند. سقف هر فایل و نسخهٔ بازشده در تنظیم مخزن ۶۴ MiB است. فایل alias پیش‌فرض خالی است؛ پوشش صفر، صادقانه گزارش می‌شود، نه با تطبیق حدسی.

## کش هوشمند و فشار روی میزبان‌ها

`health_cache.hours: 6` مدت اولیهٔ استفاده از پاسخ سالم است. پس از هر `successes_per_step: 3` موفقیت متوالی واقعی، این فاصله دو برابر می‌شود، تا سقف `max_hours: 24`. نتایج ناموفق از این کش مثبت استفاده نمی‌کنند. `hours: 0` یا `--force-check` کش مثبت را غیرفعال می‌کند؛ با `check_links: false` هیچ نتیجه‌ای تازه و سالم اعلام نمی‌شود.

نتیجهٔ کش شامل زمان اصلی بررسی و کیفیت همان مشاهده است؛ نه زمان اجرای جدید. کش، شمارندهٔ موفقیت/شکست و آخرین موفقیت را جلو نمی‌برد. در گزارش `checked_links` فقط درخواست‌های واقعاً بررسی‌شده و `cached_links` جداگانه است. سن بررسی در داشبورد با گذر زمان بیشتر می‌شود.

`host_limit.concurrent: 2` و `interval: 0.15` محدودیت درخواست هم‌زمان و فاصلهٔ شروع درخواست‌ها به هر میزبان/درگاه است؛ مقصد redirect و فرزند HLS هم محدود می‌شوند. `Retry-After` برای 429/503 با سقف `max_retry_after: 10` رعایت می‌شود. هدر Cookie/Authorization روی redirect به مبدأ متفاوت فرستاده نمی‌شود.

## بررسی اختیاری صوت و تصویر

`--playback-checks` یا `playback.enabled: true` حداکثر `max_channels: 10` کانال را برای `seconds: 3` ثانیهٔ رسانه با بودجهٔ دیواری `timeout: 20` ثانیه **برای هر کانال و مجموع ابزارها** نمونه‌گیری می‌کند. ابتدا ffprobe (اگر نصب باشد) نوع صوت/ویدئو، کُدک و ارتفاع را می‌خواند؛ سپس ffmpeg باید واقعاً خروجی رمزگشایی‌شده تولید کند. کانال‌های قدیمی‌تر/بررسی‌نشده اولویت دارند تا نمونه‌ها بین اجراها بچرخند.

- پایتون همچنان بدون وابستگی خارجی کار می‌کند؛ ابزارهای `ffmpeg` و `ffprobe` اختیاری‌اند. نبود ffmpeg به‌صورت `unavailable` ثبت می‌شود، نه موفقیت یا توقف ساخت.
- نتیجه‌ها `decoded`، `failed`، `timeout` یا `unavailable` هستند؛ شکست نمونه، به‌تنهایی مبنای حذف استریم نیست. اطلاعات در `playback.samples` و تاریخچهٔ نادیده‌گرفته‌شدهٔ `.cache/iptv/playback.json` ثبت می‌شود.
- ورودی فقط پروتکل‌های شبکهٔ موردنیاز را می‌پذیرد؛ shell اجرا نمی‌شود. تعداد کانال، مدت رسانه، پروب و زمان پردازش محدود است؛ این‌ها **سقف دقیق بایت ترافیک نیستند**. نمونه‌های با بیت‌ریت بالا هزینهٔ بیشتری دارند. کیفیت اندازه‌گیری‌شدهٔ این نمونه به بقیهٔ کانال‌ها تعمیم داده نمی‌شود و DRM باز نمی‌شود.

## علاقه‌مندی و پروفایل شخصی

`favorites.json` در ابتدا خالی است تا سلیقهٔ کاربر حدس زده نشود. با شناسهٔ اصلی کانال تکمیل کنید:

```json
{"channels": ["PressTV.ir", "IFilmEnglish.ir", "name:uk:my channel"]}
```

شناسه‌های بدون کیفیت کافی‌اند؛ نام مستعار EPG لازم نیست. برای کانال بی‌شناسه، مقدار دقیق `identity` از گزارش را استفاده کنید. کانال‌های گمشده در `missing_favorites` مشخص‌اند. `favorites.m3u` فقط کانال‌های موجود در خروجی اصلی را شامل می‌شود.

پروفایل‌ها در `profiles.json` تعریف می‌شوند؛ مثال:

```json
{
  "profiles": {
    "my-tv": {
      "languages": ["fa", "en"],
      "countries": ["ir", "us", "uk"],
      "max_resolution": 720,
      "include_unknown_resolution": false,
      "preferred_sources": ["trusted-stream-host.example"],
      "favorites_only": false
    }
  }
}
```

خروجی این نمونه `profile-my-tv.m3u` است. فیلترهای غیرخالی با **و** ترکیب می‌شوند. پروفایل واقعاً بین لینک‌های جایگزین واجد شرایط انتخاب می‌کند؛ صرفاً نسخهٔ HD پلی‌لیست اصلی را حذف نمی‌کند. اگر نسخهٔ کم‌کیفیتِ سالم وجود نداشته باشد، چیزی جعل یا تبدیل کیفیت نمی‌شود. ارتفاع تصویر سقفِ بیت‌ریت/مصرف اینترنت نیست؛ master تطبیقیِ بالاتر از سقف نیز بدون نسخهٔ مستقل مناسب پذیرفته نمی‌شود. کیفیت نامشخص تحت سقف، پیش‌فرض حذف می‌شود و تعداد حذف‌ها گزارش می‌شود؛ مجازکردن صریح آن تضمین سقف کیفیت را ضعیف می‌کند.

`preferred_sources` در پروفایل یا تنظیم سراسری، فهرست مرتب نام میزبان یا پیشوند URL است؛ هم آدرس منبع فهرست و هم میزبان استریم قابل‌ترجیح‌اند. ترجیح فقط میان گزینه‌های واجد شرایط اعمال می‌شود و لینک خراب را بالاتر از لینک سالم نمی‌نشاند. اگر زبان مشخص/قابل‌شناسایی نباشد، پروفایلِ دارای فیلتر زبان آن را نمی‌پذیرد.

حداکثر ۲۰ پروفایل با نام `[a-z0-9-]` مجاز است. حذف یک پروفایل، فایل قبلاً مدیریت‌شدهٔ آن را به M3U خالی تبدیل می‌کند تا فهرست قدیمی باقی نماند؛ فایل‌های دستیِ مدیریت‌نشده لمس نمی‌شوند. تنظیم مخزن دو نمونهٔ قابل‌ویرایش `fa-en` و `low-bandwidth` دارد.

## گزارش‌ها

- `build_stats.txt`: خلاصهٔ آخرین تغییر معنادار منتشرشده؛ کانال جدید/حذف‌شده، تغییر آدرس، تغییر کیفیت و بازیابی.
- `build_report.json`: طرح نسخهٔ ۲؛ `channel_catalog` با هویت/کیفیت/زبان/سن بررسی، سلامت، فراداده، EPG، پروفایل‌ها و نمونه‌های پخش.
- `changes`: فهرست‌های `added_channels`، `removed_channels`، `url_changes`، `quality_changes` ، `recovered_channels` و `returned_unverified_channels`. عوض‌شدن URL یا هدر همان هویت، کانال جدید نیست. کیفیت فقط با دو مقدار شناخته‌شده مقایسه می‌شود. بازگشت کانال شناخته‌شده یا رفع خطای قبلی فقط پس از **بررسی تازهٔ سالم** بازیابی محسوب می‌شود؛ بازگشت بدون بررسی تازهٔ سالم جداگانه ثبت می‌شود، نه کانال جدید یا بازیابی تأییدشده. یادآوری هویت‌های حذف‌شده تا ۹۰ روز و ۲۵هزار مورد در کش نگه‌داری می‌شود؛ پس از حذف کش، تشخیص بازگشت تاریخی محدود است.
- `index.html`: داشبورد RTL با جست‌وجو، فیلتر گروه/کشور/زبان/سلامت/EPG، جزئیات کانال، منابع، تغییرات و لینک دانلود. مستقیم با مرورگر باز می‌شود؛ نیاز به سرور، CDN، درخواست API یا پخش خودکار ندارد. فعال‌سازی GitHub Pages خودکار انجام نمی‌شود؛ برای میزبانی می‌توانید جداگانه آن را تنظیم کنید.
- `dead_links.txt`: فهرست لینک‌های ناموفق همراه وضعیت و علت؛ عنوان «ناموفق» به معنی قطع دائمی نیست.
- `.cache/iptv/last_run.json`: گزارش همان اجرای فعلی، زمان بررسی، تغییرات و علت توقف؛ حتی اگر خروجی منتشر نشود.
- `.cache/iptv/link-health.json`: تاریخچهٔ بررسی هر درخواست، زمان/کیفیت مشاهدهٔ اصلی، موفقیت/خطای متوالی و هویت‌های شناخته‌شده.
- `.cache/iptv/backups/`: نسخه‌های یکتای قبلی، با تعداد محدود.

**داشبورد و گزارش عمومی تصویر آخرین تغییر معنادارند، نه تله‌متری زندهٔ آخرین اجرا.** اگر محتوای پلی‌لیست و وضعیت گزارش‌ها تغییری نکرده باشد، فقط ساعت اجرای جدید باعث بازنویسی خروجی‌ها و commit نمی‌شود. زمان‌های داخل آن تصویر عمداً ثابت می‌مانند؛ اطلاعات تازهٔ هر اجرا در `last_run.json` و artifactهای Actions است. تغییرات داخل گزارش عمومی مربوط به انتشار همان تصویرند؛ تغییرات اجرای جاری در `last_run.json` محاسبه می‌شوند. تغییر واقعی وضعیت منابع یا لینک‌ها می‌تواند گزارش را تغییر دهد، حتی اگر خود پلی‌لیست یکسان باشد.

## GitHub Actions و تلگرام

- `Update playlist` روزانه ساعت **03:00 UTC** یا به‌صورت دستی اجرا می‌شود؛ انتشار فقط از شاخهٔ `main` مجاز است.
- ورودی‌های دستی `force_check` و `playback_checks` همان گزینه‌های CLI را فعال می‌کنند؛ در اجرای زمان‌بندی‌شده خاموش‌اند.
- قبل از ساخت، تست‌ها اجرا می‌شوند. کش منابع، تاریخچه و بکاپ‌ها با Actions Cache بین اجراها بازیابی می‌شوند؛ کش سرویس ممکن است منقضی یا حذف شود.
- اجراهای هم‌زمان سری می‌شوند. خطای پایتون پشت `tee` پنهان نمی‌شود.
- اگر `main` هنگام ساخت جلو رفته باشد، انتشار رد می‌شود تا خروجی قدیمی روی ورودی تازه نوشته نشود؛ اجرای تازه لازم است. هیچ `reset --hard` یا بازپخش خروجی قدیمی انجام نمی‌شود.
- فقط فایل‌های تولیدشده commit می‌شوند؛ `manual.m3u`، تنظیمات و حذف‌ها جزو مرحلهٔ انتشار نیستند.
- گزارش اجرای موقت و لاگ به‌مدت ۱۴ روز به‌صورت artifact نگه‌داری می‌شوند.
- برای اعلان تلگرام، Secrets مخزن با نام‌های `TELEGRAM_BOT_TOKEN` و `TELEGRAM_CHAT_ID` را تنظیم کنید. مقادیر محرمانه را در فایل‌ها یا commit قرار ندهید. بدون این تنظیمات، مرحلهٔ اعلان رد می‌شود.
- پیام با newline واقعی و JSON ارسال و پاسخ API بررسی می‌شود. در اعلان ناموفق، توکن در خطای چاپ‌شده نشان داده نمی‌شود.

workflow مستقل `Tests` روی تغییر کد/تنظیمات و pull request اجرا می‌شود و Python 3.10، 3.12 و 3.13 را پوشش می‌دهد. تست‌های عادی شبکهٔ عمومی ندارند.

### اعتبارسنجی محدود روی شبکهٔ واقعی، بدون انتشار

در اجرای دستی **Tests**، گزینهٔ `live_check` را روشن کنید؛ روی شاخهٔ آزمایشی هم مجاز است. این job مجوز نوشتن مخزن/ارسال تلگرام ندارد: منابع واقعی را می‌گیرد، حداکثر ۱۲ کانال از کشورها/میزبان‌های متنوع و ۲ نمونهٔ دیکود در هر ساخت را در `.cache/live-validation/` بررسی می‌کند، اجرای دوم را برای کش مثبت و یک dry-run را برای ثابت‌ماندن فایل‌ها/تاریخچه مقایسه می‌کند. محافظ حداقل کانال نیز **عمداً و مصنوعی** رد می‌شود و حفظ خروجی قبلی بررسی می‌شود. پوشهٔ جدید برای اجرای مجدد لازم است.

```bash
python -m iptv_builder.diagnostics --limit 12 --playback-samples 2
# یا بدون ابزارهای دیکود:
python -m iptv_builder.diagnostics --output-dir .cache/live-check-2 --playback-samples 0
```

`validation_summary.json`، گزارش سه اجرا، داشبورد نمونه و تاریخچه به‌مدت ۱۴ روز artifact می‌شوند. اعتبارسنجی نمونه جای اجرای کامل روزانه یا تست روی دستگاه/اینترنت کاربر را نمی‌گیرد. شکست منبع یا راهنمای برنامه در این آزمایش هم صادقانه گزارش می‌شود.

## تست‌ها

```bash
python -m compileall -q build_playlist.py iptv_builder tests
python -m unittest discover -s tests -v
```

تست‌ها از شبکهٔ عمومی استفاده نمی‌کنند: پاسخ‌های خطا شبیه‌سازی می‌شوند و تست یکپارچه، CLI واقعی را مقابل HTTP server محلی و در پوشهٔ موقت اجرا می‌کند. مواردی مثل fallback کیفیت، هدر لازم، HTML با کد ۲۰۰، قطع منبع و بازیابی کش، مهلت خطای موقت، محافظ افت تعداد، ثبات خروجی بدون تغییر و rollback خطای دیسک بررسی می‌شوند. پلی‌لیست‌های اصلی مخزن در تست‌ها بازنویسی نمی‌شوند. تست‌های جدید، EPG/gzip/DTD، alias پایدار، کش تطبیقی، redirect و محدودیت میزبان، تغییرات معنایی، پروفایل کم‌کیفیت، خروجی HTML ضد تزریق و ابزار دیکود را هم پوشش می‌دهند. تست دیکود واقعی با رسانهٔ مصنوعی و HTTP محلی فقط در صورت نصب ffmpeg اجرا می‌شود؛ در نبود آن صریحاً skip می‌شود.

## ساختار کد

`build_playlist.py` نقطهٔ ورود است. منطق در `iptv_builder/` به بخش‌های تنظیمات، تجزیهٔ M3U، دسته‌بندی، دریافت منابع، سلامت لینک، ذخیره‌سازی ایمن، هماهنگی ساخت، فراداده، EPG، نمونه‌گیری پخش، شخصی‌سازی، تغییرات معنایی، داشبورد، عیب‌یابی زنده و اعلان تفکیک شده است.

فهرست‌ها به منابع بیرونی وابسته‌اند. مجوز مشاهده/بازنشر و قوانین محل استفاده را رعایت کنید؛ وجود یک لینک در خروجی، مجوز محتوا یا دسترسی دائمی به آن را تضمین نمی‌کند.
