# بررسی ربات تعاملی ارسالی و اصلاحات

مبنای بررسی: سه فایل ارسالی `telegram_bot.py`، `run_bot.sh` و `BOT-README.txt`. نسخهٔ ارسالی خارج از Git بررسی شد؛ شناسهٔ شخصی داخل نمونه‌ها وارد نسخهٔ عمومی نشده است. توکن launcher ارسالی placeholder بود؛ ادعای افشای یک توکن واقعی یا الزام به چرخش آن صرفاً بر اساس این فایل‌ها نمی‌شود.

## یافته‌های مهم

| اولویت | ایراد نسخهٔ ارسالی | اصلاح |
| --- | --- | --- |
| بالا | خالی‌بودن `TELEGRAM_CHAT_ID` به معنای پاسخ به همه بود | private-by-default؛ allowlist ضروری و حالت عمومی صریح |
| بالا | ذخیرهٔ offset پیش از اجرای handler؛ احتمال ازدست‌رفتن دستور در خطا | ذخیره پس از رسیدگی، فایل اتمی، توقف در شکست ثبت و عدم عقب‌گرد خودکار |
| بالا | چاپ traceback، خطای urllib یا بدنهٔ پاسخ می‌توانست URL حاوی توکن را نشان بدهد | خطاهای نوع‌دار و پیام‌های بدون توکن/بدنه/متن کاربر؛ توکن از repr تنظیمات حذف شده |
| بالا | فقدان قفل و مدیریت اختصاصی تضاد دو poller/webhook | قفل Linux/Windows، تشخیص ۴۰۹، عدم حذف خودکار webhook |
| متوسط | `/status` آخرین workflow کل مخزن را می‌خواند؛ موفقیت تست با موفقیت انتشار اشتباه می‌شد | endpoint مخصوص `main.yml` به‌علاوهٔ فیلتر شاخه و لینک اجرای معتبر |
| متوسط | پاسخ `ok:false` و HTTP 429/`retry_after` به‌صورت یکسان با همهٔ خطاها رفتار می‌شد | اعتبارسنجی envelope، تفکیک خطای موقت/دائمی، backoff و retry_after |
| متوسط | دانلود بی‌سقف، نبود محدودیت استفاده، و کش بدون سیاست روشن دادهٔ قدیمی | سقف حجم/timeout، rate limit، TTL monotonic و هشدار stale با عمر محدود |
| متوسط | جستجو در کل EXTINF و جداکردن بعد از آخرین کاما؛ نتیجهٔ غلط برای attribute یا نام دارای کاما | جداکنندهٔ خارج از نقل‌قول، جستجوی نام واقعی، یکسان‌سازی فارسی/عربی و صفحه‌بندی |
| متوسط | تأیید callback پس از دریافت منبع؛ spinner طولانی | تأیید اولیه پیش از دریافت داده، رسیدگی به callback منقضی/پیام غیرقابل‌ویرایش |
| متوسط | نبود کنترل طول پیام بر اساس محدودیت Telegram و ایموجی | تقسیم/محدودسازی بر مبنای واحد UTF-16؛ لینک‌ها و دکمه‌ها در پیام آخر |
| متوسط | launcher لینوکس متغیرهای محیطی موجود را با مقادیر نمونه جایگزین می‌کرد | خواندن `.env` به‌صورت متن و حفظ تقدم محیط؛ بدون eval/source |
| متوسط | راهنما به `run_bot.bat` موجودنبوده اشاره داشت و توکن را وارد آدرس مرورگر می‌کرد | launcher ویندوز و discovery محلی بدون پاسخ/تأیید offset، بدون URL توکن‌دار مرورگر |
| نگه‌داری | تنظیمات سراسری در زمان import و یک فایل بزرگ، بدون تست اختصاصی | بستهٔ مستقل `iptv_bot`، entrypoint بدون side effect و تست‌های آفلاین |

## رفتارهای حفظ‌شده و افزوده‌شده

دستورات قبلی `/start /help /link /stats /status /search` و شش دسته حفظ شده‌اند. لینک داشبورد، پروفایل کم‌مصرف، پروفایل فارسی/انگلیسی و علاقه‌مندی‌های **منتشرشدهٔ پروژه** نیز اضافه شده‌اند؛ علاقه‌مندی شخصی کاربران یا دستکاری فایل پروژه ادعا نمی‌شود.

جستجو نام‌ها را نمایش می‌دهد، نه URL یا هدرهای استریم؛ ربات مستقیماً هیچ منبع ویدئویی را بررسی نمی‌کند. snapshot آخرین انتشار با مانیتور لحظه‌ای اشتباه گرفته نمی‌شود و موفقیت یک workflow تضمین پخش نیست.

## مرزهای امنیت و قابلیت اطمینان

- بدون credential واقعی، تماس زنده با Telegram، ارسال پیام، تغییر webhook یا ثبت دستورات در حساب مالک آزمایش نمی‌شود. این عملیات فقط با اجرای صریح مالک انجام می‌شوند.
- کلیدها در محیط یا `.env` خصوصی هستند؛ `.env.example` خالی است. قفل/offset در کش محلی‌اند و فایل‌های ورودی خصوصی یا فایل‌های اصلی ارسالی با شناسهٔ واقعی منتشر نمی‌شوند.
- API عمومی رسمی بررسی‌شده فقط برای توضیح پیاده‌سازی است؛ هیچ کانکتور تلگرام یا کنترل حساب مالک در این محیط ادعا نمی‌شود.
- ذخیره بعد از رسیدگی به update، تضمین دقیقاً یک‌بار نیست. crash پس از پذیرش ارسال و قبل از ذخیره می‌تواند پاسخ را تکرار کند؛ خطای دائمی ارسال عمداً از صف عبور داده می‌شود. rate limit/دسترسی نیز می‌تواند یک update را عمداً بدون پاسخ رد کند.
- قفل محلی و rate limit در حافظه به این پردازه/پوشه محدودند؛ برای مقیاس عمومی یا چندسرور، نیاز به صف، پایگاه داده و هماهنگی مشترک است. این ارتقا آن مقیاس را ادعا نمی‌کند.
- بستهٔ جدید از سازندهٔ Unix-only پلی‌لیست import نمی‌کند؛ آزمون Windows مختص ربات است. CI ویندوز و چهار نسخهٔ پایتون برای همین مرزها تنظیم شده‌اند؛ نتیجهٔ نهایی باید از اجرای واقعی خوانده شود.

## نتیجهٔ بررسی محلی

- مجموعهٔ اختصاصی ربات: **۸۶ آزمون** با موفقیت اجرا شد؛ یک آزمون مخصوص launcher ویندوز روی Linux عمداً اجرا نمی‌شود.
- کل پروژه: **۲۸۸ آزمون** با موفقیت، با دو skip صریح (launcher ویندوز و decoder اختیاریِ نصب‌نشده). آزمون قبلیِ اعلان‌های ساخت نیز همچنان عبور می‌کند.
- پوشش branch-aware کد ربات، CLI و بسته‌بندی: **۹۰٪** در همین محیط Linux؛ مسیرهای واقعی قفل Windows جداگانه در CI بررسی می‌شوند.
- Ruff، قالب‌بندی، compile و تجزیه با دستور زبان Python 3.10، syntax اسکریپت Bash و YAML/pin کامل Actions بررسی شدند.
- ZIP مستقل بدون import سازندهٔ پلی‌لیست استخراج و با config ساختگی به‌صورت آفلاین اجرا شد. بسته فقط از allowlist ساخته می‌شود؛ `.env` واقعی، state، کش و شناسهٔ شخصی نمونهٔ ارسالی در آن نیست.
- این نتایج **آزمایش زندهٔ Telegram، نصب سرویس یا تأیید حساب مالک نیستند**. نتیجهٔ واقعی CI ویندوز/چهار نسخهٔ پایتون باید در PR/Actions بررسی شود، نه از نتیجهٔ Linux استنتاج شود.

## نحوهٔ بازآزمایی

```bash
python -m compileall -q telegram_bot.py iptv_bot tests/bot
python -m unittest discover -s tests/bot -t . -v
bash -n run_bot.sh
python -m unittest discover -s tests -v
```

از `--check-config` برای بررسی محلیِ بدون شبکه استفاده کنید. راهنمای استفاده، مهاجرت offset، سطح دسترسی گروه‌ها و اجرای دائم در [BOT-README.md](../BOT-README.md) است.
