# IPTV همراه — Android phone trial

An isolated Kotlin/Compose/Media3 client for the existing catalog. **Experimental, not a production/Play release.** The user's 0.1.1 report identifies a Xiaomi phone running **Android API 31 (Android 12)**; an earlier description said Android 13. The user confirmed **0.1.3 is stable** and that **0.1.4's manual «شناور» button works on their phone**. That is not confirmation of every Home/OEM/native-menu path. **0.1.5 EPG** still needs its own phone check; emulator tests target API 31 and 33. This does not change the Python builder, production playlists, Telegram notifier, Pages, or `main`.

## 0.1.5: XMLTV programme guide

- Settings → **«راهنمای برنامه‌ها (EPG)»** configures **one XMLTV/XMLTV.gz HTTP(S) URL per catalog**, in private DataStore preferences. The URL is entered only inside the app, never requested in chat. Saving, selecting a catalog and reopening the app do **not** download a guide. Tap **«دریافت راهنما»**, or the separately labelled guide-refresh icon by the channel count. There is no periodic job, worker, background service or automatic M3U-header URL import.
- Matching selected-catalog channels show **current/next titles and their start times** in channel rows (also in favorites/history when that channel belongs to the selected catalog). Unmatched/expired data is not invented, and a guide is not borrowed from another catalog. The clock is re-evaluated every 30 seconds only while the main UI is started, without network traffic. This is a now/next list, not a full-day grid or a PiP overlay.
- XMLTV IDs match exactly and case-sensitively; channel names are not aliases. The M3U's actual, possibly rewritten `tvg-id` is kept in a private derived per-source sidecar keyed by stable channel identity and exact catalog revision. **`x-original-tvg-id`, `Channel.tvgId`, SHA-256 channel keys, Room v1, favorites and history are unchanged.** A shared saved channel may have different guide IDs in different catalogs. Existing pre-EPG catalogs should first be refreshed (file catalogs explicitly reselected) to acquire rewritten IDs; until then their existing stored TVG IDs remain available without guessing.
- Streaming **UTF-8/UTF-16 XMLTV** and gzip (file/HTTP encoding, at most two layers) are supported. Times require 12 or 14 digits; explicit offsets are respected, and a missing XMLTV zone means **UTC**, not the phone's zone. Start times display in the phone's local zone. Invalid intervals are omitted; a missing stop is inferred only from a later distinct start on the same channel, never fabricated for the last entry. Persian titles are preferred; bounded sanitized titles are plain text, not rendered HTML. Descriptions, logos and links inside XMLTV are neither stored nor fetched.
- Network limits: **8 MiB received, 32 MiB after each expansion, 250,000 programme records parsed, 20,000 programmes / 2,000,000 approximate retained characters** for selected IDs and the useful time window (6 hours past / 7 days ahead). Depth, attribute-count and 32 KiB lexical-run limits prevent giant XML allocations. External XMLTV DOCTYPE declarations are ignored without fetching; internal DTD/entity subsets and unresolved entities are rejected, including UTF-16 XXE. Truncated/invalid/gzip-bomb input cannot replace a good cache.
- A derived private `cacheDir/epg` cache is atomic, URL-hash/source-bound, at most eight files / 24 MiB total (8 MiB per file). It contains timestamps/IDs/titles, **not raw URLs/tokens**; the OS can evict it. A guide is usable for at most **48 hours**, with a warning after **24 hours**. Failed/cancelled same-feed refresh retains last-known-good data; intentionally changing/removing a URL invalidates that catalog's old guide. Bounded reads reject corrupt caches. Late downloads cannot resurrect deleted/changed catalogs or a URL changed A → B → A.
- Guide requests use the existing HTTP opt-in, TLS and redirect policy and **no media headers/cookies/authorization**. URLs reject user-info and are never copied to diagnostics, saved Activity Bundles or external Intents. The configured URL may itself contain provider query tokens, so it is stored privately, shown only in its edit dialog, and must not be shared in chat. Errors use fixed URL/XML/token-free messages. Provider hosts still necessarily see the IP/request. There is no new permission or TLS bypass.

Unit regressions and two real API31/33 UI cases are mandatory alongside all prior PiP/playback/privacy/catalog gates. They cover settings/manual download, exact IDs, local now/next times, gzip, offline disk-cache reopen, same-channel cross-catalog isolation, guide removal without saved-data loss, malformed/HTTP failures and cancellation. Test definitions are not a claim of a successful run; consult the specific Actions evidence.

## 0.1.4: native picture-in-picture

- After the first decoded video frame, tap **«شناور»** in the player to minimize it. Unsupported devices and audio-only/failed/not-yet-rendered media cannot enter PiP. A system permission refusal leaves fullscreen playback usable, with a short explanatory message.
- **Home-to-PiP is opt-in**, in Settings → «شناور شدن با دکمهٔ Home», and defaults **off**, including after an upgrade. When enabled, only active video playback may auto-enter. Manual minimization also works for an already-rendered paused video; Back/«بازگشت به کانال‌ها» always finishes playback instead of minimizing it.
- The small window is video-only: fullscreen toolbars, errors, loading overlays and Media3 controls are hidden. Android supplies expand/dismiss and immutable, package-scoped pause/play actions through a non-exported receiver; no stream URL or credentials are put in an Intent. Expansion restores the fullscreen controls and keeps the same player. `singleTask`/`onNewIntent` reuses the Activity when another channel is selected, without a second concurrent engine.
- A visible PiP Activity is normally paused but **not stopped**; `onPause` does not release it. Every actual `onStop` (including dismissal/denied entry) still detaches/releases Media3 on main and schedules the existing application-owned network cleanup on IO. There is no invisible/background audio service, notification, overlay permission or wake-lock addition.
- Android 8+ must advertise `FEATURE_PICTURE_IN_PICTURE`; the user must allow the system's PiP special access. API 31+ uses native auto-enter parameters; API 26–30 uses the guarded Home hint. Aspect ratios, including unusual/pixel-aspect metadata, stay within platform bounds. Newer transition APIs are version-guarded; the required emulator matrix is **31/33**, not a claim of testing every OEM/API.

Required new runtime cases use the **real system PiP window and UI Automator**, generated loopback AVC/AAC and main-thread StrictMode. They check manual minimize/decoded playback/expand, default-off and opted-in Home/dismissal cleanup, actual system pause/play actions plus channel reuse, denied special access, and explicit Back. No test is ignored or satisfied by invoking a fake PiP callback. See the actual workflow results rather than treating this test definition as a pass.

## 0.1.2: confirmed TLS teardown crash

The supplied private local report identifies `NetworkOnMainThreadException`, wrapped by `ActivityThread.callActivityOnStop`, from `PlaybackActivity.releasePlayer -> ConnectionPool.evictAll -> ConscryptEngineSocket.close`. Closing an **idle HTTPS** socket can write TLS `close_notify`. Calling cancel/evict from `onStop` on main was therefore unsafe. It is not evidence of an unsupported codec, RAM shortage, or a bad stream.

The outgoing client is now detached on main and handed to an **application-owned IO cleanup coroutine**, not `lifecycleScope`, so destruction does not cancel scheduled cleanup. Cancellation, pool eviction, and executor shutdown all run on IO and independently attempt completion. Cleanup captures only the outgoing client, never the activity or a later retry/resume client's resources. Media3 release and PlayerView detachment remain on the main looper. StrictMode and normal TLS validation are not weakened.

The earlier 0.1.1 lifecycle-start correction and bounded, private, manually copied Java/Kotlin fatal report remain. No messages, URLs, credentials, thread names, or source-file paths are recorded; no telemetry is sent. Android's original uncaught handler is delegated to. Native faults, OS kills and some OOM events cannot be captured. A previous report remains until manually deleted; its version identifies which build actually crashed.

### Regression coverage

The **Android API31 and API33 stability** workflow runs on Android/workflow changes and manually. Each image retains the five playback/report cases below without skips, in addition to the new source-management and mandatory version-specific upgrade phases described under Verification:

- At least 70 seconds of catalog/favorite UI activity and recreation.
- At least 75 seconds of generated loopback AVC/AAC playback, actual rotation, stop and a new engine on resume.
- Local-report read/copy/reopen/delete, with private-message omission.
- A **negative control** reproducing the old main-thread TLS pool-eviction exception on real Android Conscrypt; the test catches it inside its callback rather than crashing the process.
- Actual player `onStop`/resume/`onDestroy` with an idle TLS socket in the owned pool and main-thread StrictMode network death enabled. A test-only clone trusts a generated localhost certificate and shares the actual player's pool/dispatcher. This avoids adding a TLS bypass or injectable test hook to shipped code. Both outgoing cleanup completion and the next client's independence are checked.

The synthetic media belongs only to the instrumentation APK, never the application APK. Tests do not contact provider streams/logos and do not imply physical Poco/MIUI or live-provider compatibility. Consult the specific workflow run for results; defining a test is not evidence that it passed. Unit tests separately check IO socket closure, in-flight cancellation, repeated release, independent clients, and cleanup surviving owner-scope cancellation.

### Trial signing

The 0.1.1 -> 0.1.2 transition previously lost its cached debug identity and was not an in-place update. That is historical, not the intended upgrade path. Every CI build now requires the delivered 0.1.2/0.1.3/0.1.4 certificate, proves possession of its private key, and signs from a verified temporary file **outside all caches**. It never generates a replacement identity. `BUILD-INFO.json` records `signing_source`, `signing_key_path_verified`, `legacy_signing_cache_restored`, `private_signing_material_written_to_cache`, and certificate compatibility. Install verified updates without uninstalling or clearing data; stop on incompatibility rather than erasing saved information.

Follow the [Persian owner recovery guide](SIGNING-fa.md). The repository policy initially permits only an **explicitly transitional existing cache** if no Secret is available; it does not claim that owner recovery/Secret setup has happened. The owner creates a passphrase-protected age recovery identity locally, sends only its public recipient, and downloads only an encrypted backup. After local certificate/private-key verification, local `gh` installs `IPTV_SIGNING_KEYSTORE_B64` via stdin and Git pushes a public Secret-only policy to this branch. Secret-only builds cannot fall back to cache. Deleting the legacy remote cache is a separate guarded action, requiring recovered offline backup confirmation and successful Secret-based APK/API31/API33 upgrade/runtime evidence. Plaintext private keys are never committed or uploaded; the ciphertext-only artifact is short-lived, not the permanent backup. This retains a **DEBUG/TRIAL identity**, not a production release key.

## Current scope

- Android 8+ (`minSdk 26`), `compileSdk/targetSdk 36`, phone layout, Persian RTL dark UI.
- Media3 1.11.1 device decoders with platform decoder fallback; HLS, DASH and supported progressive HTTP(S) media. No FFmpeg or LibVLC dependency, universal-codec promise, or DRM bypass.
- A 20-channel bundled **unverified** catalog snapshot for device trials. Selected from the root `playlist.m3u` at `eb813fff5ff1e0ed668d8b2ef47b410538809cdb`, 2026-11-10. Contains HLS, a DASH URL, an HTTP entry and a header-bearing entry, but these are URL/container examples, not verified codec samples. No live stream probe occurred when selecting them.
- Online presets (Persian, fa/en, low-bandwidth, all) and **multiple independent, named M3U URL/file catalogs**. Every successful add receives a new UUID, even for the same URL/file. Manage selection, rename, refresh and confirmed deletion separately; built-in presets cannot be renamed/deleted. 8 MiB decompressed and 20,000-channel limits per catalog. An HLS stream manifest is not a channel-list M3U. Only HTTP(S), no URL user-info or local-file protocols.
- File imports use the Storage Access Framework without retaining a URI or requesting broad storage permission. Refresh explicitly asks for the file again and replaces only the target catalog; cancelling changes nothing. Adding a file always creates another catalog. Source names are bounded to 80 characters, with controls/bidi overrides removed and Persian ZWNJ preserved.
- Categories, Persian/Arabic-normalized search, logos, device-local favorites and a bounded 40-entry playback history using Room. DataStore preferences. Favorites are independent of project-published `favorites.m3u`.
- Fullscreen player, subtitles/audio controls supplied by Media3, fit/crop, rotation and native picture-in-picture as above. Playback releases the engine on actual `onStop`; no audio-only background service, notifications, recordings or Xtream login yet. Selected-catalog XMLTV now/next is described above.
- Classified, URL-free user diagnostics and manual retry. Media3's loader retries are bounded; no engine switching loops.

The `profile-low-bandwidth.m3u` preset selects supplied renditions. It does not transcode, create quality variants, or guarantee bandwidth. Source cache timestamps describe catalog imports, **not successful playback**.

## Security / privacy boundaries

- `INTERNET` plus the library-merged `ACCESS_NETWORK_STATE` normal permission; the unused Media3 `WAKE_LOCK` permission is explicitly removed because playback requires a visible fullscreen/PiP Activity; file import uses a user-picked URI, not broad storage access. No account, advertising, analytics, location or Telegram integration.
- HTTP disabled in app policy by default, with persistent opt-in only after a warning. Manifest-level cleartext support is required for arbitrary IPTV hosts, but the shared OkHttp application and network interceptors enforce policy for playlists, XMLTV guides, media manifests, redirects, segments, keys and logos. Pure HTTP data sources prevent manifest access to local files.
- HTTPS uses normal system certificate/hostname verification; no trust-all manager or custom CA bypass. User-imported raw URLs with user-info are rejected.
- Stream-specific headers are sanitized and scoped to exact scheme/host/port. They are removed on cross-origin redirects/child requests. Some providers requiring credential sharing with another CDN therefore need a future explicit, narrowly scoped configuration, not indiscriminate header forwarding.
- Imports and refreshes are bounded and parsed before a Room transaction replaces source references. Failure/cancellation preserves last-known-good data. A repository mutex serializes refresh, rename and deletion so an in-flight refresh cannot resurrect a deleted catalog. Deletion is a Room transaction that removes only that catalog and unreferenced, unsaved channels; shared channels, favorites and history survive, including deletion of the last personal catalog. Deleting a selected source returns to the bundled offline sample. The chosen external file is never modified/deleted.
- Room remains **schema v1**, without any migration. EPG aliases/cache are separate derived files, not changes to channel keys/tables. Existing `custom`/`file` source IDs, names, timestamps and DataStore selections are retained unchanged and remain manageable. A stale/missing personal selection recovers to the sample; it never invents a replacement source.
- Channel keys include URL, TVG ID and headers, so rotating tokens/URLs can produce a new favorite identity; persistent cross-refresh provider identity is future work. Identical channel identities share their metadata across catalogs, as in v1; deleting one catalog never removes a channel still referenced by another.
- Private app storage, with backup/data transfer excluded; no separate database encryption. Logos/streams/providers necessarily see the phone's IP. Turn off logos to avoid those image requests.
- Copied diagnostics include version, Android API, device model, Media3 version, error code and selected MIME formats; never the URL or request headers. Media3 logging is disabled by the application.

## Verification and next steps

CI runs pure Kotlin parser/search tests, local-loopback network policy/TLS/header tests, Room/repository tests under Robolectric **API 33**, lint, instrumentation compilation and APK signature/manifest/archive checks. Source-management regressions cover repeated URL/file adds, legacy IDs, targeted file replacement, empty/failed/cancelled refresh, name validation, protected presets, rename isolation, deletion rollback, shared/saved-channel retention and concurrent refresh/delete. DataStore tests verify selection compare-and-reset without erasing HTTP/logo/PiP settings, and that the independent Home-to-PiP preference defaults off and persists. Pure PiP-policy tests cover entry guards, paused/manual behavior and platform-safe aspect ratios. Robolectric is not an emulator or a real Poco X3; no test result implies real video/audio decoder compatibility. Main-playlist ingestion tests are offline and adapt to the checked-in playlist rather than hard-coding historical channel counts.

The API 31/33 emulator workflow rebuilds the immutable delivered **0.1.2 source** (`93b2152…`), **0.1.3 source** (`4332f07…`) and **0.1.4 source** (`b48e155…`) with the retained signer. Three independent phases seed legacy or four named URL/file catalogs, shared/saved channel identities, selected source, favorites, history and preferences, perform a real `adb install -r` to **0.1.5**, and verify preservation in fresh target processes. Earlier default-off Home-to-PiP stays off; an existing 0.1.4 Home opt-in stays on; new EPG URL preferences are empty and never auto-download. Each phase compares generated Room v1 schemas and the delivered public certificate. These are source-rebuilt baselines, **not a claim of byte-identical rebuilding of previously downloaded APKs**; actual hashes/matches and scope are recorded. Emulator reset/downgrade is allowed only before each phase's synthetic seed, never between seed and verification. The **15 runtime cases** run in separate processes: five native PiP cases first (fail-fast system UI/accessibility automation), six mandatory version-specific upgrade seed/verification cases, then all eight previous runtime cases plus two EPG cases. Each runtime phase's XML is retained and aggregated; missing/failed/skipped cases or any missing upgrade path cannot pass the gate. The system document-picker UI itself is not automated; file results are supplied programmatically. Existing prolonged synthetic playback and strict TLS teardown controls remain required. This is not physical-device/provider-stream certification.

The Room Gradle plugin declares schema exports as cache-aware task outputs for future non-destructive migrations; a cache hit must not silently omit upgrade evidence. No destructive migration fallback is enabled. Check native dependencies/ELF page alignment and licensing again before any production release; FFmpeg/LibVLC, if later introduced based on concrete device errors, need their own native, ABI, 16 KiB and license validation.

The reported manual 0.1.4 PiP success does not certify 0.1.5 EPG or every native PiP/OEM path. Add decoders/fallbacks only for concrete device errors.
